# BubbleFacts desktop app: design

The command-line setup is too technical for most musicians. This turns the
project into an app you download, open, and click through: no Terminal, no
`.env` file, no Node.js, and no separate AI install.

## Decisions

| Area | Choice | Why |
|---|---|---|
| App framework | **Electron** | Reuses the existing TypeScript server unchanged. Bundles its own Node.js and browser, so nothing else needs installing. Mature installers and updates on all three systems. |
| Platforms | **macOS 13+** (Apple silicon and Intel), **Windows 10 and 11** (x64), **Linux** x64 | Exactly where OBS 32 runs. |
| Installers | macOS `.dmg`, Windows `.exe` (NSIS, per-user, no admin), Linux `.AppImage` and `.deb` | The standard format on each system. |
| Setup | **Two steps**: 1) connect your songs (sign in with StreamerSongList, or paste a StreamElements token), 2) put BubbleFacts on your stream (drag it into OBS). The test bubble ends setup with **Start using BubbleFacts**. Originals and live learns are a link from step 2 and in Settings; custom facts are in Settings only. Everything else has a default and lives in Settings. | Every question in setup is a place to get stuck. |
| Starting up | The server starts as soon as the song list is connected. Until the built-in AI is ready, it runs with `AI_PROVIDER=none`: songs get Wikidata, MusicBrainz, song-list and custom facts. The dashboard calls the download "Getting BubbleFacts ready". | The overlay works on the first stream, even while the model is still downloading. |
| Adding to OBS | A tile in the app that you **drag into OBS's Sources list**, which makes a Browser source at the canvas size. When OBS connects, the app sends a test bubble and confirms with "It's on your stream!" The overlay reconnects within about 4 seconds (it retries every 1 to 4 seconds), so for 15 seconds after the fact server starts the dashboard says **Connecting to OBS** instead of asking to add it. | No file paths or settings to copy, and immediate proof that it worked. |
| Overlay size | Everything in the overlay scales with the height of the Browser source, with a Bubble size setting on top. **Where bubbles appear** keeps them to the top, bottom, left or right, or in one fixed spot (a new bubble there replaces the last), and the Now Playing bubble can be turned off. | Looks the same on a 720p, 1080p or 4K canvas, whatever size OBS gives the source. |
| On-air controls | **Pause bubbles** and **Show a test bubble** on the dashboard, plus Songs, Facts and Stream status and a Help and troubleshooting section. Paused, songs are still followed but nothing is shown; a fact server the app restarts (after a crash or stall) starts paused too, while quitting the app clears it. The test bubble is its own message, shown on top of the song that's playing, whose bubbles carry on. | The streamer needs a one-click way to hide it mid-stream, and to check it without playing a song. |
| StreamElements | A second song source, chosen in the first setup step ("Where do your song requests come from?") and in Settings. The musician pastes the JWT token from the StreamElements dashboard; the app tests it and saves it encrypted like the other secrets. When StreamElements refuses it, the dashboard asks for a new token in Settings. | Some musicians take requests through StreamElements' Media Request player, not StreamerSongList. StreamElements has no sign-in for apps like this one, so a pasted token is the only way in. |
| Song list sign-in | **OAuth 2 with PKCE** against id.streamersonglist.com, returning to a one-time server on `127.0.0.1:53682`. The app refreshes the hour-long access token five minutes early, saves each rotated refresh token before using it, and hands the running server the new token without a restart. Pasting a Streamer Access Token remains as the fallback. The channel is followed by its ID, so a sign-in that carries no channel name still starts. | No token to find and copy. StreamerSongList sign-in goes through Twitch. |
| AI | **Built in**, via node-llama-cpp, running Llama 3.2 3B (Q4_K_M, about 2 GB). It downloads in the background as soon as the app opens, resumes after interruptions, and retries on its own. The address is pinned to one Hugging Face commit and the file to its SHA-256; a file that doesn't match is deleted and not retried on its own (**Try again** does). **High quality** under Settings, Advanced, swaps in Llama 3.1 8B (Q4_K_M, about 5 GB, pinned the same way): about half the wrong facts in a fact check (3.4% against 7.1%), but it needs 16 GB of memory and a graphics chip that holds it, and writes 1.5 to 2 times slower. Settings warns, never blocks, below 15 GB of reported memory (a 16 GB computer reports a little less) or on an Intel Mac. A switch downloads the new model while the old one keeps writing; the server restarts on the new one when it's checked, and the old file (or its partial download) is deleted once the new one has loaded, so a model that can't run here can still be switched back without a download. The quality isn't in backups: it belongs to the computer. | No Ollama or API key needed, and no choice to make: Standard stays the default, and High quality is for computers that can carry it. Uses the Mac's GPU (Metal) and Vulkan GPUs on Windows and Linux, and falls back to the processor, then to custom facts only. Groq, Anthropic and Ollama remain in Settings. |
| Custom facts | **Your own facts** in Settings is the only place for custom facts. Settings also lists every song with its own facts (Edit, Remove). A line starting `[Song]`, `[Artist]` or `[Game]` shows only for that, first; other lines can show for any song no source knows. With none, a song no source knows gets no bubbles. The empty box shows a gray placeholder example that never goes on stream. The musician's own facts are saved as a pack in the app's data folder (`facts/`), and `TOPIC` names only that pack (or `none`). The app doesn't offer or use the example packs in `topics/`; a `topics` list saved by an older version is ignored and dropped on the next save. Saving with no custom facts is allowed. Each fact can be up to 300 characters, as for song facts (a `[Song]` tag doesn't count): the box says which line is over as it's typed, and Save is refused with that reason rather than trimming it. | The example packs were non sequiturs for most channels (a Tetris fact under a Chopin nocturne). The musician's own facts fit their music, and they add them without editing JSON. |
| Settings | A settings screen, saved as JSON in the app's data folder; the StreamerSongList and Twitch sign-ins, the StreamElements token and API keys are encrypted with the operating system's keychain (Electron `safeStorage`). Edits made in Settings stay as typed when the musician leaves Settings and comes back (to edit a song's facts, say) until they click **Save**; filling the screen again after a sign-in or Twitch connect leaves them alone, and Settings says they aren't saved yet. On a Mac the window opens before the saved sign-in is read, with a notice to click **Always Allow**: macOS asks again after each update, and the app waits on that prompt. | No text files to edit, and no secrets stored in plain text. |
| Overlay file | Copied to a fixed folder in the app's data folder on every start | OBS needs a stable path. The app's own install folder moves on updates, and on Linux the AppImage mounts somewhere new each run. |
| Self-healing | The server runs in a supervised child process. The app checks its health every few seconds and restarts it after a crash, a hang, or a stalled song-list connection, backing off if it keeps failing. | A musician mid-song can't debug anything. |
| Song facts | **Add facts for this song** under **On stream now** (or **Add facts for another song**, for one that isn't playing: picked from the StreamerSongList list as the title is typed, which carries its song ID, or typed by title and artist) saves facts for one song in `song-facts.json` in the data folder, matched by StreamerSongList song ID or YouTube video ID, else title and artist (or an alias), keeping version text ("(Acoustic)" isn't "(Remix)"). They're shown first, exactly as written, with no lookup or AI, even for a live learn; a songwriter is credited only when the streamer names one. Their link always gets its own bubble ("More from <writer>", or "More from this song's creator" with no writer), so an entry with only a link is kept. Up to 20 facts of up to 300 characters each: the editor counts characters near the limit and stops **Add another fact** at 20, and the server refuses anything over with a reason the editor shows, rather than trimming it. A save made while facts are being written for that song wins (see [Keeping generations in order](ARCHITECTURE.md#keeping-generations-in-order)). Each fact on the dashboard shows its source. | Other music content creators' originals and small artists have no source; authorship is never inferred from a tag or from who's playing. |
| About | An **About** page (top bar, footer, tray menu) laid out as GNOME's About dialog: version and support links, Credits, Acknowledgements and Legal, with each component's and data source's license. `AUTHORS.md` and `THIRD-PARTY-NOTICES.md` ship in the app. | The same on every system, since Windows has no About panel for this kind of app. |
| Twitch (optional) | **Connect Twitch** in Settings uses Twitch's device code sign-in for a public client (`twitch.ts`): Twitch's page opens with the code filled in, and the streamer checks it matches and clicks Authorize. No secret in the app and no scopes. **Fill from their Twitch About** in the song facts editor, offered when the artist ends with an @name or the link is a twitch.tv page, reads one channel's public description (Helix Get Users) into fact boxes for the streamer to edit before saving. Tokens last 4 hours and renew; a refresh token works once and lapses after 30 days unused. Disconnect, and **Remove my BubbleFacts data**, revoke it. | Another music content creator's original gets a credit and a word about them, without a second sign-in for anyone who doesn't want it, and nothing unreviewed reaches the stream. |
| Backup | Automatic: after every change to settings, song facts or Wrong marks (and at start), a copy goes in `backups/` in the data folder when something changed, keeping the last 20. **Back up…** and **Restore…** under Settings, Advanced save and restore the settings, custom facts, song facts and Wrong marks as one JSON file (`backup.ts`). Sign-ins, keys, which song list it was and which AI writes the facts are never in it, so a backup moves to another computer or account, and one someone shares can't send songs to their server. | A streamer's own facts are their work; losing them to a reinstall or a new computer shouldn't be possible. |
| Restarts and reloads | What the stream has seen is saved in `session.json` in the data folder. After a restart mid-song, or when the overlay reloads, only the bubbles still to come are sent, and earlier songs' facts aren't repeated. A fact taken off with **Wrong** stays off. | A restart on stream shouldn't replay bubbles viewers just read. |
| Wrong facts | A **Wrong** button next to each fact under **On stream now** takes the fact off the overlay at once (even mid-bubble), blocks the source it came from for that song (the Wikipedia article, or Wikidata and MusicBrainz), and drops the song's cached facts so the next play looks again. **Undo** lifts the block for the song it was pressed on. Blocks are kept per song in `wrong-facts.json` in the app's data folder (the server finds it through `BUBBLEFACTS_DATA_DIR`), so they survive restarts. Custom facts and song-list facts are removed but nothing is blocked. For the streamer's own facts (song facts or custom facts, `own` in the answer), the note says so and offers **Edit it**, which opens the song's facts or Settings at that line, instead of promising the fact won't show again. **Remove my BubbleFacts data** deletes the file. After a song, the same **Wrong** is under **Earlier songs**: it marks the fact and blocks its source for next time (hands are busy while playing), and never takes a bubble off the stream, even when that song is playing again. **Hands-free Wrong** (Settings, Bubbles; off by default) is a global key a foot pedal or Stream Deck can send: Ctrl+Alt+W, Ctrl+Alt+Shift+W (Control+Option on a Mac) or F13 (`WRONG_KEYS`). `handsfree.ts` holds it with Electron's `globalShortcut` only while it's on, lets it go on quit, and Settings says plainly when another app has it. A press asks the server for `/control/wrong-current`, which marks the bubble on stream now (or the one shown last), and the dashboard shows the usual note with **Undo**. Nothing shows on stream and there's no sound. | A wrong fact almost always means the wrong article was found, so blocking the article fixes the cause, in one click, mid-stream. A musician's hands are on the instrument, and a pedal or Stream Deck can send a key without letting go. |
| Problem reports | **"Report it (opens GitHub)"** (after **Wrong**) and **"Report a problem"** (and, in betas and release candidates, **"Send a beta test report"**) open a GitHub issue, pre-filled with the song, the fact, app version, system and recent log lines (which name the Wikipedia article used), with secrets removed. The musician reviews and submits it. **Copy report** (and, in betas and release candidates, **Copy beta test report**) puts the same report on the clipboard as text (`problemReportText` and `betaReportText` in `reports.ts`, read back from the same pre-filled address, so it carries exactly what GitHub would get), to paste in a message or in GitHub Discussions. | Reports need a person's consent. Not every musician has a GitHub account, so a report can go anywhere they can paste. Filing issues silently would need a server holding a GitHub token (see Later). |
| Error messages | Failures reach the window in plain words that say what happened and what to do: `plainError` in `plain-errors.ts` maps network codes (`ENOTFOUND`, `ECONNREFUSED`, `ETIMEDOUT`), timeouts, unreadable answers, a full disk and file permission errors to a sentence, and keeps a message the code already wrote in plain words. HTTP statuses and the original error go in the log (`errorDetail`, as `[App]` lines), and so into problem reports, never on screen. Covered: sign-in, the StreamerSongList and StreamElements tests, Connect Twitch and Fill from their Twitch About, the AI download, Ollama, updates, backup and restore, the server's restart reasons, and anything a window request throws. | A musician mid-stream can act on "BubbleFacts can't reach Twitch right now" but not on "fetch failed". The developer still gets the detail in a report. |
| Updates | The app checks GitHub Releases at start, and again when **Updates** (Settings, General) changes. **Stable** (the default) offers only full releases; **Beta** offers the newest of anything, betas and release candidates included. Only a newer version is ever offered, so switching to Stable waits for the next full release instead of going back. Installs from before this setting existed are put on Beta if they run a prerelease, so testers stay testers; a new install of a beta starts on Beta too. **Update now** downloads this computer's installer and checks its SHA-256 against the release's `SHA256SUMS.txt` (`updater.ts`); **Install now** then swaps the app: on Mac a small script replaces the bundle once the app has quit and puts the old one back if that fails; on Windows the installer runs; on Linux the AppImage is replaced. A `.deb`, an app run from the disk image, or a folder it can't write to gets the download link instead. Nothing installs without a click. A new feature release (x.y.0) reaches **Beta** at once and **Stable** three days after it's published (`STABLE_WAIT_MS`), a staged rollout: problems show up with testers first. A maintenance release (x.y.1 and on) reaches both at once. | The standard Electron updater needs a Mac app signed with an Apple Developer ID. The checksum check guards against a damaged or swapped download, not against a compromised release: the list comes from the same release. |
| Hardening | The window is sandboxed with context isolation and no Node.js. Electron fuses turn off running the app as plain Node.js, `NODE_OPTIONS` and `--inspect` (`electronFuses` in `package.json`). | Another program on the computer can't borrow the app to read its saved keys. |
| Running in the background | Closing the window keeps it running in the menu bar or system tray, with a status light; Quit is in the tray menu. Optional start at login. | Closing a window by habit shouldn't stop the overlay mid-stream. |
| Linux fact server | Linux builds ship a standard Node.js (`runtime/node`), and the fact server runs under it instead of Electron's own runtime. | The built-in AI crashed (illegal instruction) under Electron's runtime on Linux. |
| YouTube lookups | When the build has a YouTube Data API key, the app passes it to the server as `YOUTUBE_API_KEY`. For StreamElements requests from YouTube's auto-generated "- Topic" uploads only, the server asks the YouTube Data API about the video ID and uses the exact artist and track from the description instead of parsing the title. The key comes from the `YOUTUBE_API_KEY` repository secret, is written into `package.json` at build time only, is restricted to the YouTube Data API, and is never logged. Without it, nothing changes. | Titles of auto-generated uploads are often just the song name; their descriptions name the artist exactly. |
| Builds | `.github/workflows/release.yml` builds all installers on each version tag (`v*`), on macOS, Windows and Linux runners, and refuses a tag whose commit isn't on `main`. Its actions are pinned to commits. File names include the version. They go into a draft release with `SHA256SUMS.txt` and a build-provenance attestation for each file. The same workflow can be run by hand for test builds. | Each installer is built on its own system, and anyone can check a download came from this workflow. |
| Website | Static pages in `site/`, published to bubblefacts.frolic.org. The download page reads the newest full release from GitHub's API (until 2.0.0, the newest beta or release candidate) and offers the right file for the visitor's system. | Static files; no server code needed, and no page edit for each release. |

## Using StreamElements instead of StreamerSongList

The steps for streamers are in the setup guide, under
[Use StreamElements instead](https://bubblefacts.frolic.org/guide.html#song-list-se).

What's different with StreamElements:

- Facts follow the song request player: they appear while it plays and clear when it stops. Pausing keeps the current song, and resuming carries on.
- If StreamElements says a song is playing but BubbleFacts can't see which one for 30 seconds, the dashboard shows **Reconnecting** instead of all green. If that lasts two more minutes, the app restarts its fact server, which reads StreamElements' state again without touching the queue.
- StreamElements only has each video's YouTube title, so BubbleFacts works out the song and artist from it ("Ciara - 1, 2 Step (Official Video)" becomes "1, 2 Step" by Ciara). Clearly titled videos get the best facts. With a YouTube key built in, auto-generated uploads are read exactly instead (see YouTube lookups above). How titles are read: [ARCHITECTURE.md](ARCHITECTURE.md#song-sources-and-youtube-titles).
- There are no live learns, so that setting is hidden.
- If StreamElements stops accepting the token (you reset it, say), the Songs light says **Paste a new token in Settings**, and the dashboard asks for a new one.

## What stays the same

The fact pipeline (grounding, screening, topic packs), the overlay page, and the
command-line setup for people who prefer it. The desktop app starts the same
server with settings passed as environment variables.

## Later (needs accounts or decisions)

- **Code signing.** Without it, macOS says the app "can't be checked for
  malicious software" and Windows SmartScreen warns on download. Needs an Apple
  Developer Program membership ($99 a year) and Azure Artifact Signing ($9.99 a
  month). Signing also enables fully automatic updates.
- **Add to OBS automatically,** through OBS's built-in WebSocket server (OBS 28+).
  The musician enables it in OBS once; the app then creates the Browser Source.
- **Automatic problem reports,** through a small endpoint on bubblefacts.frolic.org that holds
  a GitHub token, is rate-limited, and files issues only with the musician's
  consent.
- **Other languages.** The app, the overlay and the facts are English only
  (English Wikipedia).
- **Two-PC streaming,** with OBS on a second computer. The command-line version
  can do it with `HOST` (see [CONFIG.md](CONFIG.md)); the app only serves its
  own computer.
